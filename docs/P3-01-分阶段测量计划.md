# P3-01 分阶段测量计划（待批准，尚未执行）

日期：2026-10-15。目的：在正式长时间采集 BEM 之前，用真实接口分阶段确认正确性、成本和资源占用，每一阶段的结果决定是否进入下一阶段。

**每个阶段都要你批准后才执行。** 第 0 到第 2 阶段不碰正式库：第 0 阶段不写数据库，第 1、2 阶段写入单独的试验库 `chainscope_trial`。只有第 3 阶段动正式库，而且先备份。

## 通用规则

- 命令里的 `cs` 指 `.\.venv\Scripts\python.exe -m chainscope`。
- 试验库通过环境变量切换，做完一定要移除，避免误写正式库：

  ```powershell
  $env:MYSQL_DATABASE = "chainscope_trial"
  # ...本阶段命令...
  Remove-Item Env:MYSQL_DATABASE
  ```

- 每次 `sync` 都带预算上限和 `--trace-memory`，把输出的 JSON 原样保存到 `reports\`。
- **停止条件**，任一出现就停下来把输出发我，不继续下一步：
  - 有窗口被隔离（`quarantined` 不为空，或退出码 3）。
  - 同一错误连续出现 3 次。
  - `memory_peak_mib` 超过 500。
  - 单日估算 CU 超过 100 万（免费额度每月 3000 万，约每天 100 万）。
  - 磁盘剩余空间低于 20 GB。
- **实测与推算分开记录。** 实测栏只填命令输出里的数字；推算栏写明公式和依据，并给出范围，不写成单一确定值。

## 第 0 阶段：只读测量（不写任何数据库）

```powershell
.\.venv\Scripts\python.exe python\tools\measure_sources.py --usdt-hours 1
```

- 要回答的问题：
  - BEM 从部署到现在一共有多少条 Transfer，每天的分布如何，最密集的是哪一天。
  - SQD 和 Alchemy 的条数、金额合计、指纹是否一致。
  - 两个来源的最终确认高度各落后多少。
  - 用 USDT 一小时的数据测两个来源的吞吐量。
- 成本上限：每个区间最多翻 3000 页 × 120 CU = 36 万 CU。BEM 全历史加 USDT 1 小时，最坏约 72 万 CU，约为月免费额度的 2.4%。
- 产出：`reports\m0-*.json`。

## 第 1 阶段：小范围真实核对（试验库）

范围：最近一个完整自然日。如果第 0 阶段显示那天超过 5 万条，就改为 2 小时。

```powershell
$env:MYSQL_DATABASE = "chainscope_trial"
cs init-db
cs check
cs job-create --job bem --token 0x5ce033b2bfca3af30b3e8c8457deaf776a8b695a --from 2026-10-14 --to 2026-10-15 --window-size 5000
cs pools discover --job bem
cs pools list --job bem
cs sync --job bem --max-requests 2000 --max-cu 300000 --trace-memory
cs status --job bem --max-lag-blocks 2000
cs verify-job --job bem
cs recheck --job bem --sample 5
cs query --job bem --from 2026-10-14 --to 2026-10-15
cs holders --job bem --top 20
cs holders-verify --job bem --top 5
cs market --job bem --ohlcv-limit 10
cs report --job bem
Remove-Item Env:MYSQL_DATABASE
```

这一阶段第一次碰真实接口，验证这些只在模拟数据上测过的地方：

| 要确认的事 | 相关编号 | 看哪里 |
| --- | --- | --- |
| Alchemy BSC 支持 finalized 标签；Portal 有 finalized-head | P2-12 | sync 输出的 `finality`、`rpc_finalized_head` |
| Portal 按时间换算区块，`[from, to)` 边界正确 | P2-11、P2-04 | job-create 输出的区块与区块时间 |
| eth_getCode 能查到部署区块 | P2-03 | job-create 的 `deploy_block` |
| PancakeSwap 工厂事件和 Swap 解析正确 | P1-03、P1-07 | pools list、Swap 回执抽查、recheck 的 `checked` |
| 与 Alchemy 对账一致，回执抽查通过 | P1-02、P1-06 | sync 的 `reconcile`，`window_diffs` 为空 |
| 复查逐字段一致 | P1-06、P1-07 | recheck 的 `ok` |
| 查询只统计已核实范围 | P1-05 | query 的 `coverage` |
| 持仓与链上一致（不一致可能是交易税或反射机制） | P1-04 | holders-verify |
| 真实响应的内存占用 | P2-06 | `memory_peak_mib` |
| 请求数、CU 估算与 Alchemy 后台一致 | P2-10 | sync 的 `usage`，同时截图 Alchemy 后台当日用量 |
| status 用实时高度 | P2-02 | status 的 `current_head`、`head_observed_at_utc` |
| 行情接口字段格式 | — | market 输出与 warnings |

成本上限：约 2000 次请求、30 万 CU。

## 第 2 阶段：最密集 7 天（试验库）

- 范围：取第 0 阶段 per_day 里最密集的连续 7 个自然日。
- 先删除第 1 阶段的任务，或另建一个新的试验库。具体做法执行前再和你确认，因为涉及删除。
- 运行方式：

  ```powershell
  cs sync --job bem --max-minutes 30 --max-cu 1000000 --trace-memory
  ```

  按需要重复运行，直到输出 `caught_up`。

- 中途按运行手册第 6 节做一次强退恢复，结束后运行 `verify-job`。
- 要得到的数字：每万条事件用多少秒、多少请求、多少 CU、多少存储；内存峰值；`report` 里三类查询的耗时；单次 `query` 查 7 天的耗时。
- 成本上限：100 万 CU。

## 第 3 阶段：正式库全历史回填（需要单独批准）

先根据第 0 到第 2 阶段的实测推算全历史的时间、CU 和存储，结果交给你确认后再开始。

1. 备份正式库（运行手册第 5 节），记录备份文件大小。
2. `cs init-db` 把正式库从 0005 升到 0006。只加 4 个可空列，现有 8 条历史样本不变。记录用时。
3. 依次运行 `cs check`、`job-create`、`pools discover`、`pools list`。启用哪些池子需要你确认。
4. 每次运行 `cs sync --job bem --max-minutes 30 --max-cu <按推算设置> --trace-memory`，可以分多天完成。每次运行后看 `status` 和 `quarantined`。
5. 回填完成后依次运行 `verify-job`、`recheck --sample 20`、`holders-verify --top 20`。

## 第 4 阶段：连续运行 48 小时

- 用 `register_sync_task.ps1` 注册定时任务，每 10 分钟运行一次。
- 期间每隔几小时运行一次 `status --max-lag-blocks 2000`，记录 behind 和 lag。
- 结束时运行一次 `recheck` 和 `verify-job`。
- 中途停机 1 天，确认重新开机后自动补齐。
