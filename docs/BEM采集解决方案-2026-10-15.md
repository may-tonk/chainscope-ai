# ChainScope：BEM 单币采集解决方案

日期：2026-10-15。范围：BSC 上的一个代币 BEM。依据是当前代码（包括今天未提交的 `sqd.py`、`Tally` 和 `measure_sources.py`）以及 `docs/engineering-roadmap.md`。
本文是实施方案，还没有改任何代码。编号对应《65 项问题核对》。

---

## 0. 先说两个关键判断

**① 只采 BEM 一个币时，“亿级”很可能不是真实规模。**
`measure_sources.py` 已经会计算“按 BEM 最近的速度，多少年才能达到 1 亿条”。单个中小代币的全部历史通常在几千到几百万条之间。所以第三、五、七类问题里与“亿级”相关的内存、吞吐和存储风险，要先用 M0 测出真实条数再决定投入多少。不应该为一个不存在的规模过度设计。方案仍会给每一项留出处理办法，只是优先级按实测结果调整。

**② 主数据源建议改为 SQD Portal，Alchemy 改为对账来源。**

| | SQD Portal（`sqd.py`） | Alchemy Transfers（现有） |
| --- | --- | --- |
| 分页游标 | 没有游标，按区块号流式传输，中断后从最后一个区块 +1 续传 | `pageKey` 10 分钟过期（第 8 项） |
| 区块头 | 日志自带区块号、哈希和时间 | 每个区块要额外请求一次（第 33 项） |
| 最终性 | 有 `finalized-stream` 和 `finalized-head` | 当前账号的 finalized 标签还没验证 |
| 时间换区块 | 有 `timestamps/{t}/block` | 没有 |
| 费用 | 公共端点免费，限速 20 次/10 秒 | 每次 120 CU，免费额度每月 3000 万 CU |

两个来源互相独立，正好可以用 `Tally` 按窗口对账（第 43、44 项）。**这个结论要等 M0 实测后再确认**：如果 M0 显示 SQD 和 Alchemy 的数据不一致，或者 SQD 不稳定，就退回到 Alchemy 做主源，方案其余部分不变。

## 2. 数据库改动：迁移 `0003_jobs_windows.sql`

已有的三张表不动，只新增表和列。

```sql
-- 逻辑任务：一个币一个任务
CREATE TABLE scan_jobs (
  job_id            VARCHAR(32)  PRIMARY KEY,           -- 'bem'
  chain_id          INT UNSIGNED NOT NULL,
  token_address     CHAR(42)     NOT NULL,
  source            VARCHAR(16)  NOT NULL,              -- 'sqd' / 'alchemy'
  start_block       BIGINT UNSIGNED NOT NULL,           -- 部署区块
  window_size       INT UNSIGNED NOT NULL,              -- 每个窗口的区块数，初始 50000
  parser_version    SMALLINT UNSIGNED NOT NULL,
  verified_through  BIGINT UNSIGNED NULL,               -- 连续水位：从起点开始，全部完成且对账通过的最大区块
  status            VARCHAR(16)  NOT NULL,              -- active / paused / stopped
  created_at_utc    DATETIME(6)  NOT NULL,
  UNIQUE KEY uq_job (chain_id, token_address, source)
);

-- 覆盖窗口：采集、提交和对账的最小单位
CREATE TABLE coverage_windows (
  job_id            VARCHAR(32)  NOT NULL,
  start_block       BIGINT UNSIGNED NOT NULL,
  end_block         BIGINT UNSIGNED NOT NULL,           -- 两端都包含
  status            VARCHAR(16)  NOT NULL,              -- pending / running / done / failed / split
  attempt_id        CHAR(36)     NULL,                  -- 最近一次处理它的 collection_batches.batch_id
  attempts          INT UNSIGNED NOT NULL DEFAULT 0,
  event_count       INT UNSIGNED NULL,
  amount_sum        VARCHAR(90)  NULL,                  -- Python int 精确求和
  fingerprint       BINARY(32)   NULL,                  -- Tally 指纹
  finalized_head    BIGINT UNSIGNED NULL,               -- 采集时数据源的 finalized 高度
  parser_version    SMALLINT UNSIGNED NULL,
  reconcile         VARCHAR(16)  NULL,                  -- NULL / match / mismatch / skipped
  error_type        VARCHAR(64)  NULL,
  updated_at_utc    DATETIME(6)  NOT NULL,
  PRIMARY KEY (job_id, start_block),
  KEY ix_window_status (job_id, status)
);

-- 窗口和事件的关联：重复采集同一窗口不会增加行数（第 29 项）
CREATE TABLE window_events (
  job_id       VARCHAR(32)     NOT NULL,
  start_block  BIGINT UNSIGNED NOT NULL,
  event_id     BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (job_id, start_block, event_id)
);

-- 对账或冲突时的差异证据（第 50 项）
CREATE TABLE window_diffs (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  job_id       VARCHAR(32) NOT NULL,
  start_block  BIGINT UNSIGNED NOT NULL,
  found_at_utc DATETIME(6) NOT NULL,
  kind         VARCHAR(32) NOT NULL,   -- missing_in_alchemy / missing_in_sqd / field_conflict / db_conflict
  tx_hash      CHAR(66) NULL,
  log_index    INT UNSIGNED NULL,
  detail       JSON NOT NULL
);

-- 批次表改为“执行尝试”，记录它属于哪个任务（可为空，兼容旧批次）
ALTER TABLE collection_batches ADD COLUMN job_id VARCHAR(32) NULL;

-- 金额按数值排序（第 31 项）：长度生成列 + 组合索引
ALTER TABLE transfer_events
  ADD COLUMN amount_len TINYINT UNSIGNED AS (CHAR_LENGTH(amount_raw)) STORED,
  ADD INDEX ix_amount_numeric (chain_id, token_address, amount_len, amount_raw);
```

**为什么这样设计：**
- 窗口就是断点（第 6、7 项）。SQD 没有分页游标，所以不需要保存“窗口内的第几页”。中断后**整窗重做**，靠事件唯一键保证幂等，这也是路线图 §6 要求的“重查固定窗口，不能跳到最后看到的区块 +1”。
- `verified_through` 只沿着连续的 `done` 窗口推进，所以中间有失败窗口时水位会停在空洞前面（第 11 项）。没有事件的窗口照样记为 `done` 且 event_count=0，这就是空范围的覆盖证据（第 12 项）。
- 第 31 项：要按数值排序时用 `ORDER BY amount_len, amount_raw`。聚合时，BEM 的单笔金额和总供应量都远小于 10^65，可以用 `CAST(amount_raw AS DECIMAL(65,0))`；上线前先用 totalSupply 的位数确认这一点。

## 3. 新命令和模块

| 命令 | 作用 |
| --- | --- |
| `chainscope job create bem --token <地址> [--source sqd]` | 建任务：找出部署区块，写入 `scan_jobs` |
| `chainscope sync bem [--max-runtime 50m] [--max-requests N]` | 主流程：规划窗口 → 逐窗采集 → 入库 → 对账 → 推进水位；随时可以中断，下次自动续采 |
| `chainscope status bem` | 显示水位、finalized 高度、落后的区块数和时间、pending/failed 窗口、覆盖空洞、最近错误、请求计数（第 14、58 项） |
| `chainscope recheck bem --sample 20` | 随机抽取已完成的窗口，重新拉取并比对指纹（第 46、48 项） |
| `chainscope redo bem --parser-version 2` | 把旧解析版本的窗口重置为 pending（第 49 项） |
| `chainscope query bem --from 2026-10-01 --to 2026-10-08` | 按北京时间查询；如果时间范围超过了水位，就明确提示“部分覆盖”，不会返回 0（第 1、2 项） |

- `python/chainscope/jobs.py`（新增）：负责任务、窗口规划、水位推进和锁。
- `python/chainscope/sync.py`（新增）：负责 sync 主循环。
- `database.py`：改为批量写入。

- `collector.transfer_totals`：作为对账来源。
- 现有的 `collect`、`fetch` 保留，作为单批调试工具。

## 4. `sync` 主循环（逐步说明对应的问题）

```
1. 拿锁       SELECT GET_LOCK('chainscope:job:bem', 0)
              拿不到就退出，提示“已有进程在运行”                        → 第 16 项
              MySQL 连接断开后锁会自动释放，不会留下死锁

2. 清理遗留   本任务里 status='running' 的窗口改回 pending，
              对应的 collection_batches 标为 failed(error_type='abandoned')
              （拿到锁就说明没有别的进程，这些 running 一定是遗留的）   → 第 15 项

3. 规划       head = SQD finalized_head()（同时记录 Alchemy finalized 标签，两者取较小值）
              从最后一个窗口的 end+1 开始，按 window_size 切到 head，
              生成新的 pending 窗口                                          → 第 13、14、45 项
              停机多久都一样：积压就是 pending 窗口，会自动补齐

4. 逐窗处理（按 start_block 升序，从最早的 pending 或 failed 开始）
   a. 预算检查：超过 --max-runtime 或 --max-requests 就在窗口之间安全停止 → 第 38、39、36 项
   b. 标记 running，新建一条 attempt 记录
   c. events = sqd.window_transfers(..., limit=50000)
      抛出 TooManyEvents 时：窗口对半拆成两个 pending 子窗口，
      原窗口标为 split                                                       → 第 9、10 项
      内存上限 = 5 万条 × 每条约 0.5 KB ≈ 25 MB                              → 第 17–19 项
   d. 计算 Tally（数量、金额合计、指纹）
   e. 入库：一个窗口一个事务（见第 5 节）                                    → 第 23–25 项
   f. 对账：Alchemy transfer_totals 拉同一窗口，比对 Tally                   → 第 43、44 项
      一致 → reconcile='match'
      不一致 → 两边逐条比较，差异写入 window_diffs，reconcile='mismatch'，
               水位不越过这个窗口，命令以非 0 状态退出                       → 第 50 项
   g. 回执抽样：在本窗口里用固定种子随机抽 3 笔交易做回执核验              → 第 41、42 项
   h. 推进水位：沿着连续的 done+match 窗口更新 verified_through              → 第 11 项
   i. 输出一行 JSON 日志到 logs/sync-YYYYMMDD.jsonl：
      窗口、事件数、耗时、条/秒、请求数、429 次数、事务耗时                 → 第 57 项

5. 释放锁，打印汇总
```

**为什么第 46–48 项（链变化、重组、迟到事件）这样处理就够了：** 只处理 finalized 以内的区块，BSC 的 finalized 区块不会再被重组。SQD 返回 409 时直接停止，不自动修复。`recheck` 用随机抽样加 Alchemy 对账来发现“当时漏返回、后来补上”的迟到事件，发现后写入 diffs，再用 `redo` 重做。这一点要在 README 里写清楚：**已最终确认的区块出现冲突时，系统会停下来等人工处理，不会自动覆盖。**

## 5. 入库改造（`database.store_window`，第 23–29 项）

```
BEGIN
  SELECT ... FROM coverage_windows WHERE job_id=? AND start_block=? FOR UPDATE
  -- 批量查已有事件，每 1000 条一组，替代逐条 SELECT
  SELECT event_id, tx_hash, log_index, <所有字段>
    FROM transfer_events
   WHERE chain_id=56 AND (tx_hash, log_index) IN ((?,?), ...)
  逐条对比内容：不一致 → 写 window_diffs(kind='db_conflict')，ROLLBACK，窗口标为 failed
  -- 批量插入新事件
  INSERT INTO transfer_events (...) VALUES (...), (...), ...      -- executemany，每组 1000 条
  再查一次拿到新 event_id
  INSERT IGNORE INTO window_events (job_id, start_block, event_id) VALUES ...
  UPDATE coverage_windows SET status='done', event_count, amount_sum, fingerprint,
         finalized_head, parser_version, attempt_id=? ...
  UPDATE collection_batches SET status='succeeded' ...
COMMIT
```

- **第 25 项（大事务）**：一个事务只包含一个窗口，最多 5 万条，锁的持有时间可以控制。
- **第 26 项（断线、死锁）**：遇到错误码 1213（死锁）、1205（锁等待超时）、2006/2013（连接断开）时，重连后重试整个窗口事务，最多 3 次，间隔 1、2、4 秒。
- **第 27 项（提交结果不确定）**：COMMIT 时连接断开的话，重连后先读 `coverage_windows`。如果 `attempt_id` 等于本次尝试且 status 为 done，就说明已经提交，继续往下走；否则按未提交处理，重做这个窗口（幂等）。
- **第 28 项（并发竞争）**：GET_LOCK 保证同一任务只有一个进程。插入时如果仍然撞上唯一键（1062），就当作“已存在”，回到对比流程，不让整个批次失败。
- **第 20 项（`.all()` 一次读回）**：`verify_window` 用 `yield_per(5000)` 流式读取，在 Python 里重新计算 Tally，再和窗口记录比对，内存只占一组。
- **第 21 项（响应大小）**：SQD 是按行流式读取的，单行超过 8 MB 就报错。Alchemy 每页最多 1000 条，`rpc_client` 检查 `Content-Length`，超过 16 MB 就报错。
- **第 30 项（结构检查）**：`check` 改用 `alembic.autogenerate.compare_metadata` 比较实际数据库和 `models.py`，列出缺失或不同的列、索引和约束。

## 6. 请求与预算（第 32–40 项）

| 项 | 做法 |
| --- | --- |
| 32 串行 | BEM 单币先保持串行（SQD 本身也限速）。只有 M0 显示回填超过 24 小时才考虑并发 |
| 33 区块头 | SQD 日志自带区块头，不用额外请求 |
| 34 回执成本 | 每个窗口只抽 3 笔，并计入请求计数 |
| 35、40 额度和历史能力 | 由 M0 实测给出：BEM 总条数、SQD 用时、Alchemy CU 用量、两边是否一致 |
| 36 全局预算 | `--max-requests` 和每日 CU 上限（默认每月免费额度的 1/30），对账请求也计入 |
| 37 Retry-After | `rpc_client` 学 `sqd.Portal._backoff` 的做法：优先读 Retry-After，否则指数退避，最多等 60 秒 |
| 38、39 时间预算 | `--max-runtime`，在窗口之间检查，到时间就停；下次 sync 自动接着做 |

## 7. 无人值守运行（第 56 项）

- 用 Windows 任务计划程序每 10 分钟运行一次 `chainscope sync bem --max-runtime 9m`。GET_LOCK 保证不会重叠运行；电脑休眠或重启后，下一次触发自动补齐积压。
- `status` 显示落后时间超过 15 分钟（第 5 项的默认值）时，用退出码 2 表示“落后”，以后可以接通知。现在不配置任何外发通知。

| 链上买入、卖出 | SQD Portal 的 Swap 日志 + 交易发起人 + 同一笔交易里的 Transfer | 见 10.2 | `dex_pools`、`swap_events` | M6 |
| 钱包持仓、前 80 名 | 由 Transfer 累计重建，用 `balanceOf` 抽查 | 见 10.3 | `balance_checkpoints`、`address_balances` | M7 |
| 区块时间、交易回执、地址是否为合约 | BNB Chain RPC（Alchemy 或公共节点） | 见 10.4 | `address_info` | M1 起逐步加入 |
| 价格、市值、24 小时成交量 | CoinGecko API | 见 10.5 | `market_snapshots` | M8 |
| 主池价格、储备、4 小时 K 线和成交量 | GeckoTerminal API | 见 10.5 | `pool_snapshots`、`pool_ohlcv` | M8 |

**原则：链上事实和第三方数据分开存放，分开标注来源。**
- 链上事实包括 Transfer、Swap、余额和区块时间，都可以对账和复现。
- 第三方数据包括 CoinGecko、GeckoTerminal 和标签，只保存“哪个时间点从哪里取到了什么”，不当作链上事实使用。
- 网页上展示时，两类数据都要注明来源和时间。

### 10.2 链上买入、卖出（Swap）

1. **确定交易池**：
   - 用 SQD 拉 PancakeSwap V2 工厂的 `PairCreated` 和 V3 工厂的 `PoolCreated` 日志，筛出 token0 或 token1 是 BEM 的池子。
   - 你手工确认后写入 `dex_pools`，字段包括：池地址、DEX、版本、BEM 在 token0 还是 token1、报价币（WBNB/USDT/…）、创建区块、`enabled`。
   - 只采集 `enabled` 的池子。新池子出现时只提示，不自动加入。
2. **采集 Swap 日志**：复用窗口流水线，每个池子建一个 job（`bem-swap-<池子>`）。SQD 查询时同时取交易字段（`from`、`hash`），这样不用为每笔交易再请求一次 RPC。
   - V2 Swap topic0：`0xd78ad95fa46c994b6551d0da85fc275fe613ce37657fb8d5e3d130840159d822`，金额字段是 `amount0In/1In/0Out/1Out`。
   - V3 Swap topic0：`0xc42079f94a6350d7e6235f29174924f928cc2ac818eb64fed8004e115fbcca67`，金额是有符号的 `amount0/amount1`。
3. **判断买卖方向**：池子付出 BEM（BEM Out > 0）就是**买入**，池子收到 BEM 就是**卖出**。
4. **判断是谁在买卖**：Swap 日志里的 `sender` 和 `to` 往往是路由合约，不是真正的用户。规则如下：
   - 默认取 `tx.from`（交易发起人）作为交易者；
   - 再看同一笔交易里的 BEM Transfer：买入时，看池子把 BEM 最终转给了谁；卖出时，看谁把 BEM 转进了池子。如果它和 `tx.from` 不一致，就记录实际收款地址；
   - 每条记录都带一个 `attribution` 字段，取值为 `direct`（发起人直接收付）、`router`（经过路由合约，但能对应上）或 `ambiguous`（聚合器或多跳交易，对应不上）。前 80 名的买卖统计默认只用前两类。
5. **`swap_events` 字段**：chain_id、pool、block_number、block_time_utc、tx_hash、log_index、tx_from、side、bem_amount_raw、quote_amount_raw、quote_token、trader、attribution、parser_version。唯一键是 (chain_id, tx_hash, log_index)。
6. **对账**：池子的 BEM 净流入流出要等于 Transfer 表里进出这个池子的 BEM 合计。按窗口用 Tally 比对，不一致时写入 `window_diffs`。

### 10.3 钱包持仓与前 80 名

1. **起点**：如果 Transfer 是从部署区块开始完整采集的，那么所有地址在部署前的余额都是 0，这就是“已核对的历史余额”。不从部署区块开始的话，必须先在起点区块对所有相关地址做 `balanceOf` 快照，成本很高，所以**推荐从部署区块开始**。
2. **累计**：
   - `address_balances(address, balance_raw, last_block)` 随水位增量更新：每完成一个窗口，就把这个窗口的转入减转出，在同一个事务里累加进去。
   - 每 10 万个区块保存一次 `balance_checkpoints(block, address, balance_raw)`，用来重建任意区块的余额：先找最近的检查点，再加上之后的转账。
3. **校验**：
   - 所有地址余额之和等于 `totalSupply`（可以用 eth_call 在同一区块查询）；
   - 前 80 名地址在检查点区块用 `balanceOf` 逐个核对。这需要 Alchemy 的历史状态查询，免费套餐支持，每次 26 CU；
   - 出现负余额就直接报错。
4. **必须先确认代币机制**：如果 BEM 是转账收税、反射分红或 rebase 类型的代币，余额不能只靠 Transfer 累计（`balanceOf` 会和累计值对不上）。M0 阶段读一下合约源码，并用第 3 步的抽查来发现这种情况。
5. **前 80 名**：从 `address_balances` 按 `amount_len, balance_raw` 倒序取。同时用 `address_info` 和 `address_labels` 标出池子、交易所、销毁地址和合约地址，另外给一个“排除池子和销毁地址后”的排名。

### 10.4 区块时间、回执、是否合约（BNB Chain RPC）

- **区块时间**：SQD 已经提供。另外每个窗口抽 1 个区块，用 RPC 的 `eth_getBlockByNumber` 核对哈希和时间（`measure_sources.compare_hashes` 已经有这个逻辑）。
- **回执**：就是第 4 节第 4g 步的随机抽样，同时覆盖 Transfer 和 Swap。
- **是否合约**：`address_info(address, is_contract, code_hash, checked_block, checked_at)`。在需要展示的地址（前 80 名、交易者）上调用 `eth_getCode`。代码以 `0xef0100` 开头的是 EIP-7702 委托账户，单独标记为 `delegated`，不算普通合约。注意合约可能在之后才部署，所以要记录 `checked_block`。

### 10.5 CoinGecko 与 GeckoTerminal

- **CoinGecko**：先确认 BEM 的 coin id。可以用 `/coins/binance-smart-chain/contract/<地址>` 反查，**必须你确认**，防止同名币混淆。之后每 10 分钟调用一次 `/simple/price?include_market_cap=true&include_24hr_vol=true`，写入 `market_snapshots(source, coin_id, fetched_at_utc, price_usd, market_cap_usd, volume_24h_usd, raw_json)`。
- **GeckoTerminal**：
  - 对 `dex_pools` 里的主池，调用 `/networks/bsc/pools/<池子>` 获取价格和储备，写入 `pool_snapshots`；
  - 调用 `/networks/bsc/pools/<池子>/ohlcv/hour?aggregate=4` 获取 4 小时 K 线，写入 `pool_ohlcv(pool, timeframe, bucket_start_utc, open, high, low, close, volume_usd, fetched_at_utc)`，唯一键是 (pool, timeframe, bucket_start_utc)，最新一根未收盘的 K 线允许被覆盖。
- **交叉核对**：GeckoTerminal 的储备和链上 V2 池的 `getReserves()` 对比；4 小时成交量和 `swap_events` 同一时段的汇总对比。差异只记录，不修正第三方数据。
- **限速和密钥**：两家的免费接口都有每分钟调用次数限制，统一走一个带 Retry-After 处理的 HTTP 客户端。如果使用 API key，要放在 `.env` 里，不进代码和日志。

### 10.6 交易所等地址标签

- **配置文件**：`config/address_labels.yaml` 纳入 git，每条包括：地址、名称（如 “Gate 热钱包 3”）、类别（cex/pool/project/burn/other）、来源链接、添加日期、`verified: false/true`。
- **入库**：导入到 `address_labels`，一个地址可以有多条来自不同来源的标签。
- **原则**：
  - 只用公开来源，比如区块浏览器公开标签页、交易所官方公布的地址；手工抄录，不批量抓取违反服务条款的网站；
  - 默认都是“未核实”，网页上展示为“疑似 Gate”；
  - 只有满足可靠条件才改为已核实：例如交易所官方公告，或者能观察到明确的充提行为。
- 标签只影响展示和统计分组，不改动任何链上数据。
