## 2. 登录保护什么，第一版交付到哪里

### 2.1 当前实际项目

截至本次只读核查，README 明确现有采集 Agent 适用于单机本地操作者，不提供公网多用户认证。`agent_runtime.py` 使用 `config/agent_local.toml` 保存本地身份；该文件不是网站用户系统，必须保留。现有源码没有因本文而获得公网认证能力。

### 2.2 第一版实际功能范围

- 公共页面：项目介绍、注册、邮箱验证、密码设置、登录、服务及隐私说明。
- 登录后：个人工作台、自己的基本账户信息、验证当前密码后修改密码、退出当前设备、退出所有设备。
- 工作台只展示已经实现的功能；研究功能未接入时明确标注尚未开放，不伪造研究结果或可用按钮。
- 后续研究会话、私人报告、任务记录必须绑定网站 `user_id`，但本轮不实现研究工作流。

第一版不开放现有 Agent 的准备/启动/停止采集、预算管理、数据修复、SQL、shell、迁移或本地操作者历史记录。不能把全部网站账户映射为同一个本地 owner，也不能直接把公网请求转交现有聊天入口。

网站登录证明账户身份；是否能执行采集、花费模型额度以及访问某份报告，是后续业务授权问题。现有本地操作者的记录不自动转移给网站用户。

### 2.3 第一版不做的功能与明确代价

- 不做忘记密码：没有找回入口或可调用的重置 API，不发送密码重置邮件，不使用注册验证码覆盖已有密码。
- 忘记密码且无法提供当前密码时，第一版无法恢复该账户。新注册另一个账户也不继承旧数据；不通过私信、SQL 改密码或邮箱相同等捷径恢复归属。
- 不做邮箱换绑、社交登录、多因素认证、管理员网页、支付、研究记忆与完整研究 Agent。
- 上线前应对注册用户明确说明“第一版暂不支持密码找回”，并支持密码管理器与粘贴。注册验证邮件仍必须实际可用。

## 3. 前端技术与部署方式

### 3.1 前端选择

建议 React＋TypeScript＋Vite，原因是后续将增加研究会话列表、任务状态、流式回答、报告查看等交互，适合维护共享登录状态及组件。选择它是产品演进判断，不代表纯 HTML/CSS/JS 无法满足安全要求。

- React：页面和组件；TypeScript：前端数据类型；Vite：开发与生产构建。
- 第一版不引入 Next.js、服务端渲染、复杂全局状态库或大型 UI 框架。
- 开发/构建需要兼容的 Node.js 和包管理器，依赖使用锁文件；具体版本在实施时核对并锁定，不能使用不固定的 latest 镜像上线。
- 生产环境运行构建后的静态文件，不向公网提供 Vite 开发服务器；采用静态部署时不需要常驻 Node.js 服务。
- 前端路由保护仅用于体验；后端每个受保护接口仍必须校验身份与权限。
- 开发工具（2026-10-23 用户说明）：前端用 VS Code 编辑，打开 `frontend/` 文件夹作为工作区；Python 后端和采集继续用 PyCharm；数据库继续用 Navicat。两边的工具各管各的目录，互不混用。
- 默认配套（实施时核对兼容版本并写入锁文件）：npm 管理依赖（本机已有）；`react-router` 负责页面切换；样式使用 Vite 自带的 CSS Modules，不引入额外样式框架；前端测试用 Vitest＋Testing Library。

建议页面：`/register`、`/register/verify`、`/register/password`、`/login`、`/app`、`/account`。不提供 `/forgot-password` 的可用流程。

### 3.2 公网部署的逻辑关系与待定位置

必须分开确定三件事：前端静态文件放在哪里、FastAPI/Agent 进程在哪里运行、数据库在哪里保存。本文没有确定整站或后端部署到 Linux；已讨论的 Linux 用途是 Agent 相关数据存储，账户库是否也放在那里仍待审核。

逻辑上的推荐入口是：浏览器通过一个应用地址访问页面，`/api/` 请求路由到 FastAPI。前端可以在静态托管平台，后端可以在另一台服务器或平台，数据库再通过受控网络连接；也可以在确认后采用部分同机部署。具体平台、网络能力及成本需要另行比较，本文不预先选择。

- 建议前端和 API 对浏览器使用相同协议、主机、端口，减少跨域 Cookie 与 CORS 配置复杂度；同源是浏览器看到的地址关系，不要求服务物理同机，可通过平台路由或反向代理实现。
- 公网 HTTPS 由选定平台或反向代理提供；HTTP 重定向 HTTPS；正确处理证书续期。稳定验证后启用合适的 HSTS，不在不了解其他子域名的情况下启用全域策略。
- FastAPI 只通过受控应用入口提供必要 API；数据库和其他内部服务不向浏览器开放。若后端与 Linux 数据库不在同一网络，需要先落实私网、VPN/隧道或受控加密连接、访问白名单和连接池能力，不能直接暴露数据库供任意来源连接。
- 只信任明确配置的代理转发头，不能相信任意客户端的 `X-Forwarded-For`；校验允许的 Host，避免伪造来源绕过限速或生成错误链接。
- 本地开发通过 Vite 代理 `/api` 访问开发后端；开发配置不能被用于公网，生产缺少 HTTPS 或必要秘密时拒绝启动。
- 开发、测试、生产使用独立数据库和秘密；生产运行使用正式服务进程管理，不开 reload/debug。

采用单机、多机或托管平台尚未确定；单机方案存在整机故障单点，不能宣传为高可用。各组件运行位置、数据库位置、域名、邮件服务、备份位置及目标并发在实施前分别确认，不预先声称吞吐或 SLA。

## 4. 邮箱、用户 ID 与注册流程

### 4.1 账户身份

每个账户由后端生成随机 UUID `user_id`，长期保持稳定。邮箱是登录标识，不作为用户表主键，不暴露到资源 URL；后台任务和私人资源关联 `user_id`。

第一版建议限制为常见 ASCII 邮箱，去除地址首尾空白并完成严格格式/长度校验，域名按域名规则处理；本产品明确采用邮箱登录不区分大小写的规则，统一生成 `email_key` 并建立唯一约束，同时保留已验证的显示地址。该规则不宣称覆盖所有支持大小写敏感地址的邮件系统。不能删除地址中的点或 `+` 后缀、推断两个别名属于同一账户。未来扩展国际化邮箱需要单独评估。

### 4.2 推荐注册流程：先验证邮箱，再设置密码

1. 浏览器取得短时匿名流程 Cookie 和 CSRF token，提交邮箱申请注册验证。
2. 后端先校验格式与限速，生成请求编号和安全随机验证码，保存验证请求；通过实际邮件服务发送。返回统一接受信息，不透露该邮箱是否已有账户。
3. 用户提交请求编号及验证码。后端验证浏览器流程绑定、用途、有效期、错误次数及是否已使用。
4. 成功后，签发仅能用于完成该邮箱注册的随机注册凭证。凭证短时、单次使用，服务端只保存校验值；验证成功不等于已经建立登录会话。
5. 用户设置密码并接受必要服务条款后，后端验证注册凭证、密码策略和邮箱唯一性。
6. 在一个数据库事务中消费注册凭证、创建用户、保存密码哈希。数据库唯一约束解决并发注册，不采用先 SELECT 再无约束 INSERT。
7. 注册成功后跳转正常登录页。若网络断开无法确认注册是否成功，提示尝试正常登录；不能盲目重新创建账户。

已有账户不可因走注册流程而被覆盖密码、取得登录会话或改变邮箱验证状态。重复注册在接口状态、提示及流程差异上应避免给未验证者提供账户存在性线索；邮箱所有权验证后的提示可以更具体，但不得成为密码重置通道。

### 4.3 注册验证初始参数

| 项目 | 初始设计值，实施需验收 |
| --- | --- |
| 验证码 | 安全随机 6 位数字，不使用普通伪随机数 |
| 验证码有效期 | 5 分钟，按服务端时间判断 |
| 错误次数 | 每个请求最多 5 次，邮箱级累计限制不能随新请求清零 |
| 重发间隔 | 同一邮箱至少 60 秒 |
| 发送量 | 同邮箱每小时最多 5 次；同 IP 每小时初始上限 20 次，另设整体邮件预算 |
| 注册凭证 | 至少 256 位安全随机数，10 分钟有效，单次消费并绑定邮箱、用途及浏览器流程 |

重发后使旧请求失效；并发提交时只有一次可消费成功。验证码保存为使用独立服务端密钥的 HMAC，并绑定请求编号、邮箱和用途；不能只保存可快速穷举的普通数字哈希。

验证码、注册凭证不进入 URL、分析脚本、日志或 localStorage。邮件已被服务商接受不等于送达；超时、退信和失败要可观察，界面不能误报已验证或注册成功。采用维护中的邮件客户端及密码库，不自研密码学。

## 5. 密码规则与存储

### 5.1 当前 NIST 要求的说明

用户提出“不强制大小写和符号组合”与当前 NIST 方向一致。但 NIST SP 800-63B-4 §3.1.1.2 对单因素密码登录要求至少 **15 个字符**；作为多因素认证一部分的密码才允许最低 8 个字符。注册时收一次验证码不构成日常登录的第二因素。

因此本文建议最低 15 字符，最大 128 字符，支持空格、长口令和密码管理器，不强制字符组合，不要求无原因的定期换密。这里是项目主动采用的安全基线，不表示已取得 NIST 认证或法律合规结论。来源见文末 [S1]。

### 5.2 执行规则

- 前后端采用相同长度定义；后端最终校验，不能只依赖前端。
- 支持 Unicode 时统一按 NFC 规范化后按 Unicode 码点计数，注册和登录规则一致。
- 不对密码去首尾空格、转小写或静默截断。超过上限明确报错，允许粘贴和自动填充。
- 设置或修改密码时，检查本地常见/泄露弱密码拒绝列表及明显的项目特定弱密码；不向外部服务发送完整密码。
- 使用维护中的 Argon2id 密码库，例如实施时核验兼容版本的 `pwdlib[argon2]`；库负责安全随机盐、编码和验证，不用普通 SHA256/MD5 代替密码哈希。
- Argon2id 至少达到 OWASP 推荐配置之一，例如内存 19 MiB、迭代 2、并行度 1，并在实际运行认证后端的目标环境按预期并发测量后确定参数；该环境目前不限定为 Linux 数据库机器。限制哈希并发和输入大小，避免请求耗尽 CPU/RAM。[S3]
- 保存完整的编码哈希和参数；不保存明文或可逆加密密码，不把密码哈希返回前端、送入模型或写入日志。
- 密码算法参数升级支持成功登录后重新哈希；不需要知道或找回原密码。

## 6. 正常登录与失败保护

正常登录：邮箱＋密码 → 规范化邮箱查账户 → 密码库验证 → 检查账户状态 → 创建新登录会话 → 设置 Cookie。不会发送登录验证码。

### 6.1 账户存在性保护

- 邮箱不存在、密码错误、账户被禁用等认证失败，对外统一返回 `401` 和 **“账号或密码错误”**，不返回内部原因或不同错误结构。
- 对不存在的邮箱执行等价的预置密码哈希验证，减少明显的快速返回时间差；先做限速再做高成本哈希。
- 不同路径尽量保持相近行为，不声称可消除所有网络计时侧信道。
- 请求格式错误可以报告格式问题，但不能包含“此邮箱未注册”等账户存在性提示。

### 6.2 多进程共享限速

初始建议（邮箱级冷却存在恶意锁号问题，修正建议见 13.4）：同邮箱标识 15 分钟内连续失败 5 次后冷却 15 分钟；同 IP 初始限制每分钟 20 次登录尝试，另设服务整体并发/请求预算。数值是待压力及误伤测试调整的产品配置，不是规范的固定要求。

- 邮箱标识对应的计数对存在和不存在的账户都创建，使用 HMAC 键避免在限速记录中直接暴露邮箱。
- 不采用无限期锁号，不让未登录者轻易永久锁死别人的账户；冷却后可自动恢复。仅 IP 限制不能防分布式猜测，单个邮箱限制也要防恶意锁号。
- 限制触发时统一返回 `429`、通用提示及必要的 `Retry-After`，不能只对真实账户显示锁定提示。
- 计数必须原子更新并由所有 Web Worker 共享。第一版可用 PostgreSQL 限速表和行锁/原子更新，经过测量后再决定是否引入 Redis；不能只用 Python 进程内字典。
- 认证数据库或限速存储不可用时，登录/注册返回通用暂不可用，不放行、不跳过保护；已登录请求无法确认会话时同样不放行。
- 从可信代理获取 IP；IPv6、共享出口和代理场景纳入误伤测试。IP 仅用于保护，不把 IP 固定绑定为账户身份。

## 7. 登录会话、Cookie 与 CSRF

### 7.1 服务端会话

第一版采用随机不透明令牌＋服务端数据库会话，不采用仅靠前端存储或无法即时撤销的独立 JWT 登录方案。

- 使用至少 256 位安全随机令牌；浏览器 Cookie 保存原令牌，数据库保存以 `AUTH_SESSION_KEY` 计算的 HMAC-SHA256 指纹及密钥版本，不保存原令牌。密钥轮换策略必须明确，第一版可以撤销全部会话后切换新密钥并要求重新登录。
- 每次登录签发新令牌，不复用匿名流程标识；权限提升需重新认证并轮换会话。
- 每次受保护请求验证：令牌存在、未撤销、未超过绝对/空闲有效期，且关联账户仍启用。服务端时间按 UTC 保存，展示按北京时间。
- 初始建议绝对有效期 7 天、空闲有效期 24 小时，两者任一到达均失效；活动时间更新应避免每请求无条件写放大，同时不能突破失效规则。
- 退出当前设备：先持久撤销服务端会话，再清除 Cookie；复制的旧 Cookie 必须立即不可用。其他设备按原规则继续有效。
- 退出所有设备：需要有效会话、CSRF，并验证当前密码（与第 9 节接口表一致），然后撤销该用户全部会话。账户禁用同样立即阻止访问，不只隐藏前端入口。
- 已登录修改密码要求当前密码、CSRF 和限速，更新后撤销全部旧会话并要求重新登录；不是忘记密码找回。
- 不把登录令牌放入 URL、localStorage、前端日志或模型上下文。

### 7.2 生产 Cookie

主 Cookie 建议命名 `__Host-chainscope_session`：`HttpOnly; Secure; SameSite=Lax; Path=/`，不设置 `Domain`。Cookie 的到期时间不晚于服务端会话有效期；清除时使用匹配的名称、Path 和作用域。

`HttpOnly` 限制脚本读取令牌，`Secure` 要求 HTTPS 传输，`SameSite` 减少部分跨站请求风险；这些属性不能代替后端鉴权、CSRF 或 XSS 防护。[S4]

### 7.3 CSRF 必须覆盖登录前与登录后

- 使用维护中的同步 token 或签名双提交方案；本文建议服务端流程/会话绑定的 CSRF token，由同源接口返回，前端存在内存并通过请求头提交。
- 注册申请、注册验证、完成注册、登录、退出、退出所有设备、修改密码等改变状态的请求都检查 CSRF；登录前使用匿名流程 Cookie，登录成功后轮换。
- 校验允许的 Origin；按明确规则处理 Referer 回退，不能因来源缺失而默认放行。生产 API 不开放任意来源的凭证 CORS。
- 不以 GET 执行退出、修改密码或注册完成；`SameSite=Lax` 和“只接收 JSON”都不能单独作为完整 CSRF 方案。[S5]
- 页面尽量不加载第三方脚本；禁止直接插入不可信 HTML，设置合适的 CSP、`frame-ancestors`、`nosniff` 及敏感页面 Referrer 策略，实施时用浏览器验证。

## 8. 数据模型与事务

建议在独立 PostgreSQL 应用库使用以下表；名称与字段为待实施合同，不是现有表。密码和网站认证记录不得混入链上事件表。Navicat 继续作为数据库管理工具。

| 表 | 核心字段/约束 | 职责 |
| --- | --- | --- |
| `app_users` | `user_id UUID PK`、`email`、`email_key UNIQUE`、`password_hash`、`email_verified_at`、`status`、`auth_version`、`password_changed_at`、`created_at`、`updated_at` | 长期账户与密码哈希；认证版本用于并发撤销 |
| `auth_challenges` | 随机请求编号、邮箱键、`purpose`、验证码 HMAC、密钥版本、浏览器绑定校验值、错误次数、有效期、验证/消费时间、注册凭证哈希 | 注册邮箱验证及注册完成授权 |
| `auth_sessions` | 随机会话记录编号、`token_hash UNIQUE`、密钥版本、`user_id FK`、`auth_version`、CSRF 校验信息、创建/活动/绝对过期/撤销时间 | 可撤销登录状态 |
| `auth_rate_limits` | 用途、HMAC 邮箱键或来源键、窗口、计数、冷却时间；原子更新约束 | 多 Worker 共用保护 |
| `auth_events` | 事件编号、时间、可空用户编号、请求编号、事件类型、脱敏来源、受限内部原因码 | 认证审计，不保存秘密 |

匿名 CSRF 流程也需要共享存储，可在认证流程存储中保存，不能依赖单进程内存。具体字段在实施时与选用组件核对，避免为同一职责重复建表。

用户创建、注册凭证消费在同一事务；验证码验证/错误计数使用行锁或原子条件更新，防止并发重放。完成注册失败时不留下可登录的半成品账户。登录会话必须提交成功后才能发送认证成功响应与 Cookie。密码修改与撤销旧会话在同一事务。

账户修改密码、禁用或退出所有设备时，在事务中递增 `auth_version`；会话记录创建时的版本，每次访问比对账户当前版本。密码哈希验证可在受限线程池完成，但建立会话的事务必须重新核对账户状态、密码/认证版本与验证前一致，防止“旧密码验证刚通过，密码已被另一个请求修改，却仍创建新会话”的竞争。版本不一致时拒绝本次登录，不能直接把旧验证结果绑定到新版本。

账户和密码哈希没有短期 TTL；过期验证请求和过期会话按独立保留策略清理，清理不能误删账户。审计初始建议保留 30 天，来源 IP 等个人信息最小化、访问受限；最终保留期及隐私说明由用户审核。

新增 PostgreSQL 时独立管理应用迁移及版本表，明确与 MySQL `0001～0009` 的边界；不得把 PostgreSQL 表塞入现有 MySQL metadata/迁移链。初始化和升级作为显式维护操作，普通请求、Web 启动不自动执行 DDL。具体目录方案须先检查现有 Alembic 配置后提交，不创建更深业务目录。

## 9. API 合同与数据权限

| 接口（统一 `/api` 前缀） | 功能 | 身份/保护 |
| --- | --- | --- |
| `GET /auth/csrf` | 初始化或取得当前流程 CSRF token | 同源、限速、`no-store`；不返回登录令牌 |
| `POST /auth/registration/request` | 申请注册邮件 | 匿名流程绑定、CSRF、共享限速、统一接受响应 |
| `POST /auth/registration/verify` | 验证注册邮箱 | 验证码次数/有效期、CSRF、单次消费 |
| `POST /auth/registration/complete` | 注册凭证＋密码，创建账户 | 不能覆盖已有账户；唯一约束和事务 |
| `POST /auth/login` | 邮箱＋密码登录 | CSRF、共享限速、统一失败响应、轮换令牌 |
| `GET /auth/me` | 当前账户的必要公开资料 | 服务端会话；禁止返回密码哈希/秘密 |
| `POST /auth/logout` | 退出当前设备 | CSRF、服务端撤销；无会话时按幂等规则处理 |
| `POST /auth/logout-all` | 退出全部设备 | 有效会话、CSRF、提交并验证当前密码；共享限速 |
| `POST /auth/password/change` | 当前密码＋新密码 | 有效会话、当前密码验证、CSRF、限速、撤销旧会话 |
| `POST /auth/account/delete` | 注销账户（待审核，见 13.1） | 有效会话、当前密码验证、CSRF、限速；同一事务删除个人数据并撤销全部会话 |

接口没有忘记密码/邮件重置能力。统一错误体建议为 `code`、`message`、`request_id`；`401` 表示未认证，`403` 表示不允许的操作或 CSRF 失败，`429` 表示限速，`503` 表示暂时无法确认服务状态。业务资源不属于当前用户时可统一 `404`，减少泄露资源存在性。

客户端不能指定自己是哪位用户。API 从已验证会话取得 `current_user_id`，只读取或修改其资源。UUID 不可猜测性不是权限控制，所有读取、下载、导出、修改和删除都需要同样的归属检查。第一版普通用户不能修改 role、status、邮箱验证标记等敏感字段。

## 10. 秘密、日志与公开仓库

### 10.1 环境秘密

会话相关密钥、CSRF/验证码密钥、数据库和邮件服务凭证只从服务端环境读取。初始部署可用服务器受限权限的 `.env`，不放在静态网站目录、镜像层或前端目录；后续可接专门秘密管理服务。

分开命名和用途：`AUTH_SESSION_KEY` 用于会话令牌指纹，`AUTH_CSRF_KEY` 用于 CSRF 方案所需的签名/绑定，`AUTH_EMAIL_CODE_KEY` 用于验证码校验，`AUTH_RATE_LIMIT_KEY` 用于限速来源键。均由密码学安全随机源生成，至少 256 位。不同用途不共用密钥，不把这些密钥当作可逆加密用户密码的工具。

- `.env.example` 只保留变量名和空值/无效占位，生产缺少秘密时拒绝启动，不使用默认演示密钥。
- 密钥由部署者在本地/服务器生成，不要求用户发送到聊天；明确密钥轮换及旧会话失效策略，不在每次重启时重新生成。
- 当前 `.gitignore` 已忽略 `.env`、`.env.*` 并例外保留 `.env.example`；忽略规则不能移除已被 Git 跟踪的秘密。提交前还须核对跟踪文件、暂存差异与秘密扫描。
- 前端 `VITE_*` 变量会进入客户端构建，任何人均可能读取，绝不放数据库密码、会话密钥、邮件密钥或模型 API Key。[S7]
- 若秘密泄漏，先撤销/轮换；删除文件或补 `.gitignore` 不代表泄漏已解决。仓库继续 PUBLIC，不以改私有替代处理。

### 10.2 日志和缓存

所有应用、代理、错误监控与邮件组件禁止记录请求中的密码、新密码、验证码、注册凭证、Cookie、Authorization、密码哈希和带凭证连接串。认证接口不记录原始请求体；错误详情对外脱敏，关闭生产调试 traceback。

可记录请求编号、内部用户编号、事件类型、时间、脱敏/最小化来源及受限错误原因。日志有权限、轮转和磁盘上限。认证响应及账户敏感响应设置 `Cache-Control: no-store`，代理/CDN 不缓存用户私人响应，不把表单数据送入第三方分析工具或 LLM。

本节为执行者需要提供的证据，不是本文已经通过的测试。模拟通过、真实邮件验证、临时数据库集成、浏览器与公网验收必须分别记录。

| 编号 | 必须验证的场景 | 通过标准 |
| --- | --- | --- |
| A01 | 不存在邮箱、错误密码、禁用账户 | 对外均为相同认证失败状态/结构及“账号或密码错误”；不存在用户也走等价哈希校验 |
| A02 | 连续失败、换 Web Worker、伪造代理头 | 限速/冷却跨进程有效；换请求编号不能重置邮箱累计保护；不信任任意转发头 |
| A03 | Cookie 检查、会话固定攻击 | 公网具备 HttpOnly/Secure/SameSite、正确作用域；登录后令牌轮换，匿名令牌不能当登录令牌 |
| A04 | 跨站注册、登录、退出、修改密码 | 缺失/错误 CSRF 或不允许来源被拒绝；单靠打开外部页面不能代用户操作 |
| A05 | 过期、当前退出、全部退出、禁用账户 | 服务端立即拒绝对应旧令牌；不是只删除浏览器 Cookie；全部退出缺少当前密码或 CSRF 时被拒绝；退出不自动停止现有采集 |
| A06 | 密码存储与策略 | Argon2id、无明文；15～128 字符/空格/Unicode 策略一致；不强制组合；拒绝弱密码；无静默截断 |
| A07 | 验证码过期、重发、重放、并发验证 | 次数限制有效；旧码失效；只能消费一次；请求绑定正确 |
| A08 | 已有邮箱重复注册、并发完成注册 | 不覆盖密码/越权登录；只出现一个账户，事务失败不产生可登录半成品 |
| A09 | 用户 A 请求用户 B 的对象/修改用户编号 | 后端拒绝且不泄漏内容；账户只能读取和更新允许字段 |
| A10 | 会话库或限速库中断 | 认证不放行，不改用进程内缓存假装通过；恢复后可继续按正式记录验证 |
| A11 | 真实邮件投递与失败 | 验证码实际送达及可使用；失败/退信可定位，无虚假注册成功 |
| A12 | 日志、构建文件和公开仓库检查 | 没有密码/令牌/验证码/密钥；Vite 构建无服务端秘密；正式账户无默认密码 |
| A13 | 真实公网浏览器与代理 | HTTPS、Cookie、CSRF、同源、页面刷新和直接访问保护均正确；数据库无公网入口 |
| A14 | 无密码找回的边界 | 前端无可用找回入口，后端无重置通道；注册验证码不能重置已有密码；注册前说明限制 |
| A15 | 已登录修改密码与并发旧登录 | 必须校验当前密码及 CSRF；成功后旧密码/旧会话不可用；并发旧密码验证不得创建有效新会话，新密码能正常登录 |
| A16 | 数据备份及独立恢复 | 应用库备份受保护，可恢复到账户/会话结构；恢复旧备份时撤销全部恢复出的会话/注册凭证并换相关密钥，避免重新激活历史凭证 |
| A17 | 多用户并发与资源预算 | 在约定目标并发（见 13.6，待用户给出数值）下测延迟、哈希内存/CPU、数据库连接、限速与邮件预算；记录结果，不虚构容量 |
| A18 | 与原项目兼容 | 现有 CLI/本地 Agent 的身份、数据、迁移链和保护规则保留；网站普通账户不能触发采集或付费请求 |
| A19 | 注销账户 | 需要有效会话、当前密码及 CSRF；成功后全部会话立即失效、无法再登录；个人数据按 13.1 处理；同一邮箱可重新注册且不继承旧数据 |
| A20 | 恶意锁号 | 攻击者持续对某邮箱输错密码，不能让真实用户从其他来源长期无法登录；规则见 13.4 |
| A21 | 开发邮件模式 | 控制台模式只在开发环境可启用；生产配置为控制台模式时拒绝启动 |

如存在越权、CSRF 缺失、无法撤销会话、生产秘密泄漏、密码明文存储、共享限速无效等问题，不得以“功能先少一点”或“测试多数通过”批准公网开放。

5. 经单独配置授权后接入注册邮件、已确定的预发布平台/服务器、HTTPS 和真实浏览器验收；若采用 Linux 数据库，另行验证后端到它的安全连接。生产迁移前审阅并确认目标及恢复点，不复制全量链上数据库来测试账户系统。
6. 提供第 11 节证据和未完成项，由用户检查后决定是否开放公网注册。

预期改动类型包括 `python/webapp/` 下平铺的 Web/认证模块、独立应用数据库迁移、按 3.3 组织的前端源码和必要工具配置，以及已有 README/operations/database-migrations 的对应更新。依赖、构建和工具生成目录按既有约定排除。具体文件数量与组件选择在实施计划中确定，本文不授权重构现有采集模块或新建 CLAUDE.md 等额外说明文件。

## 13. 审核补充（2026-10-22）

本节为审核时补充的问题与建议。标注“待审核”的仍需用户确认，执行者不得当作已批准。

### 13.1 注销账户（第一版实现；2026-10-23 用户确认采用立即彻底删除）

面向公网收集邮箱即属于处理个人信息。按《个人信息保护法》，个人有权要求删除其个人信息，第一版应提供删除途径。

- 接口：`POST /api/auth/account/delete`，要求有效会话、当前密码、CSRF 和共享限速。
- 同一事务内：撤销该用户全部会话，删除 `app_users` 中的邮箱、`email_key` 和密码哈希（建议直接删除账户行），失效该邮箱未完成的注册请求。
- `auth_events` 中的 `user_id` 改为可空并在删除时置空，或只保留不含邮箱的事件；审计按原保留期到期清理。
- 删除后同一邮箱可重新注册，新账户不继承旧数据。删除不可撤销，页面需明确提示。
- 隐私说明须写明：收集哪些信息（邮箱、审计中的最小化来源信息）、用途、保留期限和删除方式。

### 13.2 部署位置（开发用 Linux 虚拟机；公网用海外云服务器）

2026-10-22 用户确认公网上线选择海外云服务器，因此不涉及 ICP 备案；服务商、地区、配置和数据库是否同机稍后确定。下表保留比较过程：

本机上的 Linux 虚拟机默认只有本机或局域网能访问，而且要求电脑保持开机，适合开发阶段运行 PostgreSQL 和后端。公网访问可选：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| 云服务器（VPS） | 稳定公网地址，适合正式上线 | 月费；**中国大陆机房的域名需要 ICP 备案**，香港及海外机房不需要 |
| 虚拟机＋内网穿透（如 Cloudflare Tunnel） | 不需要公网 IP 和开放端口，就能把虚拟机服务暴露出去 | 电脑必须一直开机；需要一个域名和对应账号；家庭网络稳定性决定可用性 |
| 只在本地开发 | 不对外开放 | 不能算上线 |

结论：开发阶段使用虚拟机；公网使用海外云服务器，具体选型在功能和本地验收完成后进行，不阻塞开发。若后端在海外而 MySQL 链上库仍在本地，第一版认证不依赖链上库；以后需要访问时，再单独设计安全连接。

### 13.3 注册邮件服务（必需；服务商待定）

注册流程以邮箱验证为前提，所以公网上线必须有能实际发出邮件的服务；开发阶段不需要。用户已接受邮件可能进入垃圾箱，但仍须在注册页提示用户检查垃圾邮件文件夹。

| 阶段/方案 | 适用 | 注意 |
| --- | --- | --- |
| 开发：控制台模式 | 本地开发和测试，验证码只写入本地后端控制台 | 生产禁止（A21）；控制台输出不得进入共享日志 |
| 个人邮箱 SMTP（QQ 邮箱、163 等，使用授权码） | 无需自有域名，可最快上线，适合少量用户 | 每日发送量有限，大量发送可能被限制或封号；授权码作为秘密放在服务端 `.env` |
| 专业发信服务（阿里云邮件推送、Resend、Brevo 等） | 有自有域名后使用，送达率和统计更好 | 需要在域名 DNS 配置验证记录；有免费额度，超出收费 |

建议：代码只依赖一个发信接口，通过配置切换实现；开发用控制台，首次上线用个人邮箱 SMTP，有域名后再换专业服务。

### 13.4 防恶意锁号（修正第 6.2 节规则；2026-10-23 用户确认采用“邮箱＋来源”冷却加邮箱级逐步延迟）

第 6.2 节“同邮箱 15 分钟失败 5 次后冷却 15 分钟”会让攻击者每 15 分钟输错 5 次，就使真实用户长期无法登录。建议改为：

- 冷却按“邮箱标识＋来源”组合计数：同一来源对同一邮箱失败 5 次后，该来源对该邮箱冷却 15 分钟，其他来源不受影响。
- 邮箱级只设较宽的总上限（初始建议每小时 100 次失败），超出时对新的尝试逐步增加等待时间，而不是封锁所有来源。
- 来源取自可信代理头；对外响应仍统一为 `429` 和通用提示。
- 数值在测试中调整，记录误伤结果。

### 13.5 已统一的不一致

第 9 节要求“退出所有设备”验证当前密码，第 7.1 节和 A05 原先未写明，现已统一为需要有效会话、CSRF 和当前密码。

### 13.6 并发验收目标（待用户给出）

A17 需要一个目标值才能判定通过。初始建议：开发虚拟机上 20 个同时在线用户、每秒 5 次登录请求；上线前根据选定服务器重新设定。
